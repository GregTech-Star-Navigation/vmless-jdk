# 支持矩阵

> 状态：已实测 · 2026-11-17 · 口径见文末「怎么复核」
> 一句话：**JVM 指令层面**解释器覆盖 177/202、JIT 覆盖 157/202；**Java 语言层面**常规 OOP + 泛型擦除 + 异常 + 枚举 + 接口都通，
> lambda / 方法引用 / record / 文本块 / 装箱 / 非静态内部类 / 线程 / 反射 都不通。

本文件里的每个 ✅ 都对应一次真实执行：要么是仓库 `samples/` 下的样例跑过三路对照（解释器 / JIT / HotSpot 输出逐字节一致），
要么是 `docs` 编写时单独写的探针程序（下表的「依据」列写明是哪一个）。
⚠️ 的意思是「语法通得过，但语义没做到」—— 这类最容易被误判成支持。

## 一、JVM 指令（202 条，逐条）

统计（`node scripts/opcode-support.mjs --stats` 的实际输出）：

```
总指令 202 · 解释器 177 · JIT 157 · 两边都有 156
只有解释器（21）: fload fload_0 fload_1 fload_2 fload_3 fstore_0 fstore_1 fstore_2 fstore_3 dup2
                  i2f l2f f2i f2l f2d d2f i2b i2c i2s fcmpl fcmpg
只有 JIT（1）: iinc
都没有（24）: fconst_0 fconst_1 fconst_2 dup_x1 dup_x2 dup2_x1 dup2_x2 swap
              fadd fsub fmul fdiv frem fneg jsr ret tableswitch lookupswitch
              invokedynamic monitorenter monitorexit wide goto_w jsr_w
```

三条结论值得单独说：

1. **float 整体没有**。`fadd/fsub/fmul/fdiv/frem/fneg/fconst_*` 两边都没实现，编译器也不生成 float 指令
   （`codegen/` 里没有任何 float 发射点）。double 反而是通的（`Doubles`、`DblCorpus` 样例）。
2. **`iinc` 只有 JIT 有**（解释器缺，编译器也不生成，所以不影响样例）；`i2b/i2c/i2s` 只有解释器有 ——
   JIT 跑「窄化转换」（`(byte)x`）会报 `JIT 暂不支持字节码 0x91`。
3. **`tableswitch` / `lookupswitch` 一条都不生成**：`switch` 在 codegen 里降级成比较链
   （`switch(String)` 是 `equals` 链，`switch(enum)` 比 ordinal）。语义对，但分支多时比真 JVM 慢。

| `assert` | ❌ | 探针 `PAssert` | 解析成 `Stmt::Empty` 后编译报错 |
| `var` 局部变量推断 | ❌ | 探针 `PVar` | 生成的字节码被 HotSpot 判 `VerifyError: Bad type on operand stack` |
| 装箱 / 拆箱（`Integer x = 5`） | ❌ | 探针 `PBox` | 同上 VerifyError；语法过、字节码不合法 |
| 非静态内部类（隐式 `this$0`） | ❌ | 探针 `PInner` | `未找到实例方法` |
| 线程（`new Thread()`） | ❌ | 探针 `PThread` | 没有 `java.lang.Thread` 内建 |
| 反射（`Class.forName`） | ❌ | 探针 `PReflect` | 没有 `Class` 内建 |
| `float` 算术 | ❌ | 指令表 | 相关指令一条都没实现 |
| `long` / `double` 全链路 | ✅ | `samples/LongEdge`、`samples/DblCorpus` | 2 槽布局、常量、比较、JIT 返回精度 |

### 跨编译单元（包名 / import / 跨文件继承）

`verify.sh` 里给这四条留了专门的组，但**在当前提交（`615311d`）上四条都编译不过**：

```
PkgA:pkg.PkgA    依赖 PkgB PkgC   → 未找到实例方法 `get`
Import1:app.Import1              → 未找到实例方法 `plus`
Import2:app2.Import2             → 未找到实例方法 `plus`
InhUnitB:InhUnitB  依赖 InhUnitA → 找不到类 `Base`
```

用工作树里更新的二进制（`bin_l9/`，2026-11-17 05:57）重测 `PkgA` 组：`PkgB.class`/`PkgC.class` 都写出来了，
入口 `PkgA` 仍失败 —— 也就是说不是「没实现」，是**跨单元解析有 bug**。`scripts/verify-samples.sh` 对这四组做了
「样例文件不在就跳过」的处理，所以 CI 不会被它拖红；等修好后把四个文件放进 `samples/` 就自动生效。

## 三、怎么复核

指令表由脚本从源码现算，不是手抄：

```bash
node scripts/opcode-support.mjs --stats   # 只有数字和清单
node scripts/opcode-support.mjs           # 完整 Markdown 表（本文件第一节就是它的输出）
```

脚本读的两个文件、判定口径：

| 引擎 | 源码 | 取什么 |
|---|---|---|
| 解释器 | `rustjavac/src/vm/exec.rs` | 每个 `match op { … }` 分支里的 opcode（含 `0x15..=0x19` 范围式）|
| JIT | `rustjavac/src/jit/translate.rs` | 同上 |

语言特性表的复核命令（两方对照；装了 JDK 25 就是三方）：

```bash
cargo build --release --manifest-path rustjavac/Cargo.toml --bin rustjava
cargo build --release --manifest-path rustjavac/Cargo.toml --example compile_src --example run_jit
bash scripts/verify-samples.sh          # 20 个代表样例
bash scripts/verify-samples.sh --all    # samples/ 下全部
```

### 探针清单

语言表里标「探针」的那些程序是临时写的，模板长这样（改成对应特性即可）：

```java
public class PXxx { public static void main(String[] a) { /* 只测这一条特性 */ } }
```

编译 → 跑解释器 → 跑 JIT → 三方（或两方）比对输出与退出码；不一致或编译报错就记 ❌。
`PBox` / `PVar` 这两个是「我们两个引擎都输出对，但 HotSpot 拒绝加载这个 class 文件」——
按「能不能被真 JVM 接受」判失败，因为产物本来就是给 JVM 生态用的 `.class`。
