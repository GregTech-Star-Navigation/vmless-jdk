# 架构

> 状态：已核对源码 · 2026-11-18 · 对应提交 `2e7cfb1`
> 逐文件的模块清单在 `rustjavac/docs/模块结构.md`（那份是重构记录，本文件讲的是「数据怎么流动」。

## 一句话

一条编译流水线，两个执行引擎，一层自研内存管理，一套 native 层替代品。没有 JVM，没有 `jvm.dll`。

**关键取舍**：JDK 的类库**不自己重写**（`java.base` 7350 个类），而是让自研 VM **执行 OpenJDK 编好的 `.class`**；
VM 之下的一切（字节码解释、JIT、GC、类加载、native、JPMS、线程与监视器）都是自研。

```
                      ┌──────────── 编译期（rustjavac） ────────────┐
  Foo.java ──► front ──► sema ──► lower ──► codegen ──► Foo.class
               词法/语法   符号表    中间表示   字节码生成
                                                    │
                      ┌───────────── 执行期 ────────┴──────────────┐
              Foo.class ──► vm/（解释器）                    ──► 输出
                        └─► jit/（Cranelift → 机器码）  ──► 输出
                                    │
                               librustjrt（分代堆 / TLAB / 写屏障 / 根集）
```

三个入口（`rustjavac/src/bin/`、`rustjavac/examples/`）：

| 可执行文件 | 源码 | 干什么 |
|---|---|---|
| `rustjava.exe` | `src/bin/rustjava.rs` | 读一个 `.class`，用**解释器**跑 `main`，退出码同 JVM |
| `compile_src.exe` | `examples/compile_src.rs` | 读 `.java`，写 `.class` 到输出目录（输出目录同时当 classpath）|
| `run_jit.exe` | `examples/run_jit.rs` | 读 `.class`，**JIT 编译** `main` 后执行，`stderr` 打编译/执行耗时 |

## 编译流水线

四个阶段，每个阶段只认上一步的产物，跨阶段没有回头修改（`sema` 会改写 AST，但它只读源码 AST、产物是符号表）：

| 阶段 | 目录 | 输入 → 输出 | 说明 |
|---|---|---|---|
| 前端 | `front/`（`lexer/`、`parser/`、`ast.rs`）| 源码文本 → `ast::CompilationUnit` | 不做类型检查；上下文关键字按标识符处理 |
| 语义 | `sema/`（`symbols.rs`、`enums.rs`、`nested.rs`、`qualify.rs`、`erase.rs`、`resolve.rs`）| AST → 符号表 + 改写后的 AST | 枚举降级成普通类、嵌套类型拍平 `Outer$Inner`、同包简名补全、泛型擦除 + 桥接方法、跨单元解析 |
| 中间表示 | `lower/` | AST → 供 codegen 用的结构 | 体量小，主要做语法糖归一 |
| 后端 | `codegen/`（`emit.rs`、`expr.rs`、`stmt.rs`、`method.rs`、`class.rs`、`types.rs`）| AST → `ClassFile` | 自己算 `max_stack`/`max_locals`、栈图帧、异常表 |

`codegen/emit.rs` 是这里的心脏：字节缓冲、栈深记账、标签与跳转回填、StackMapTable 帧、异常表都在它身上。
两个和「正确性」直接相关的历史坑（都是 0.40 修的，写在 CHANGELOG 里）：

- **栈深按槽数记账**，不是按参数个数 —— 否则 `f(true, 7, 10L)` 之后深度永久少 1；
- **会分叉的子表达式先进脏槽**（`Emit::alloc_scratch`），保证跳转点栈恒空 —— 否则 `println(a == b)` 这类
  「比较结果当实参」写不出合法栈图。

`.class` 的读写是独立一层 `classfile/`（`pool.rs`/`attr.rs`/`read.rs`/`write.rs`），**只依赖 std**，
所以既能当编译器后端，也能被 JVM 侧的东西直接用（0.4.0 用它把 JDK 自身 33,191 个 class 读入再写出，逐字节一致）。

## 两个执行引擎

两个引擎**互不调用、共享布局**：局部变量槽是 8 字节（引用是 64 位指针，int 读写低半），
`Slot` 值模型（`vm/slot.rs`）与 JIT 侧的 `i64` 槽一一对应，所以 JIT 编译的方法能被解释器调，反之亦然。

| 关注点 | 解释器 `vm/` | JIT `jit/` |
|---|---|---|
| 入口 | `run_class_bytes` / `run_class_file` | `Jit::compile_static` + `CompiledMethod::call` |
| 类加载 | `ClassStore::load_dir`：把入口所在**目录树**里的 `.class` 全读进来（带包名的按子目录递归） | `load_class_path`：同目录，懒注册类布局 |
| 方法解析 | `class.rs` 的方法表（沿继承链 + 接口 default 回落） | `(类标签, 签名) → 实现` 的 `vcall` 方法表 |
| 异常 | `VmError { exc: Some(句柄) }` 逐帧向上找 handler | `jit/exc.rs` 的哨兵 + handler 派发 |
| 不支持的指令 | `未实现的字节码 0x.. @pc=..` | `JIT 暂不支持字节码 0x..` |
| 分配 | `vm/heap.rs`（对象/数组/字符串池，句柄是下标+1，数组是负数区分） | `vmless_new_object`/`new_array` 等运行时符号，最终都进 `librustjrt` 的分代堆 |

**两个都留着**是有原因的：三路对照（HotSpot / 解释器 / JIT）是仓库的验收手段（`verify.sh`、
`scripts/verify-samples.sh`）。只有两个独立实现才能互相暴露「看起来对」的错 —— 事实上有多个 bug 就是这样露出来的。
JIT 遇到不支持的字节码会**报错而不是猜**，这也是为了不掩盖差距。

`jit/refmap.rs` 是 JIT 侧和 GC 的接缝：记录「每个 pc 上操作数栈哪一位是引用」，GC 点（`new`/`newarray`/`invoke*`/`<clinit>`）
前后 push/pop 根；`roots_pop` 带平衡断言，不平衡直接报错，不会悄悄截断根集。

## 内存层（`librustjrt`）

不是「一个 bump 分配器」那么简单，现在是完整的分代堆：

| 部分 | 文件 | 做法 |
|---|---|---|
| 对象头 | `object.rs` | **8 字节**（`class_id` + flags 里放字段数/尺寸类/转发标记），比 16 字节版本省一半头开销 |
| 布局 | `layout.rs` | 每个类一份引用位图，GC 按**对象自己的类**扫引用（早期是全局单类布局） |
| 分配 | `alloc.rs` / `young.rs` | 年轻代 bump + **TLAB**（`Cell` 无锁）；≥64K 或 ≥eden 直接进老年代独立链表（LOS） |
| 回收 | `young.rs` / `old.rs` | 年轻代复制式清理（转发指针写在对象头里，不需要哈希表）+ 老年代标记清扫（`major()`）|

配套的 `rustcore` 是另一条线（给 OpenJDK 的 javac 名字池用），与本流水线无关。

## native 层（`vm/nat_*.rs`）

JDK 里有一批方法是 `native` 的（OpenJDK 源码里带 `native` 关键字，**本身没有 Code 属性**）。
它们只能由 VM 提供实现。判据一句话：**这个方法在 OpenJDK 源码里带 `native` 吗**？
带 → 进 native 表；不带 → 它有字节码，就该由解释器执行，**不许在这里写第二份实现**。

按「哪个领域」分成六个文件，各自 `register(r)`，`native_reg.rs` 的 `register_all` 末尾各调一次
（这样几条并行工作线各改各的，不会在 `native_reg.rs` 上撞车）：

| 文件 | 覆盖 | 关键约束 |
|---|---|---|
| `nat_intrinsics.rs` | `Unsafe`(68) / `reflect.Array`(21) / `Class`(28) / `ConstantPool`(18) | 裸内存走 `nat_mem` 假地址空间；`get_mem` **必须按 width 截断**（符号扩展 vs 零扩展会让 CAS 永不相等） |
| `nat_os.rs` | `FileDescriptor` / `FileInputStream` / `FileOutputStream` / `RandomAccessFile` / `WinNTFileSystem`(19) / `ProcessImpl` | 错误码按 `java.io` 语义映射（`FileNotFoundException` 带 Win32 本地化文本） |
| `nat_util.rs` | `VM` / `System` / `Thread` / `Inflater`(11) / `Deflater`(10) / `CRC32` / `LibFallback`(28) / `HostLocale`(26) | DEFLATE 解压是完整实现；压缩用 stored 块（合法流，压缩率 ≈1.0004） |
| `nat_nio.rs` | `WindowsNativeDispatcher`(59, 含整套 ACL/Token) / `Net`(36) / `FileDispatcherImpl`(21) / `IOUtil`(12) / `NetworkInterface`(12) | 凡把缓冲区地址交给 Win32 的，地址都是假地址 → 必须「拷进真内存 → 调 → 拷回」 |
| `nat_misc.rs` | `ClassLoader`(6) / `Thread.start0` / `Module`(5) / `StackWalker`(7) / `Perf`(7) / `reflect`(6) | 做不到的**明确抛 `UnsupportedOperationException`**，不静默返回 0 |
| `nat_desktop.rs` | AWT/Java2D：`BufImgSurfaceData` / `GraphicsPrimitiveMgr.register` / `ShapeSpanIterator`(19) | 接管 `GraphicsPrimitiveMgr` 而不是实现上千个 loops 函数指针 |

**三条铁律**（都是踩出来的）：

1. **`add_override` 有白名单** —— `exec.rs::is_override_owner` 里的类名才算数，不在里面注册了
   也永远不会被调用（死代码）。
2. **`java/lang/invoke/*` 不走 native 表** —— `exec.rs` 的三条 invoke 分支先判前缀交给
   `indy.rs::invoke_api`，在那里注册是死代码。
3. **做不到就抛异常**，不许返回 0 让上层拿到黑图 / 空数据 —— 那会把「没实现」变成「静默算错」。

## 边界

**已经不缺的**（早期文档写「设计上没有」，现在都有）：JNI（196/236 槽位）、线程与监视器、
反射与注解、类加载器、jar / jimage / JPMS、`float` 全链路、`java.desktop` 离屏渲染。

**仍然没有的**（详见 [状态.md](状态.md)）：

| 缺什么 | 后果 |
|---|---|
| **帧栈模型** | `Thread.getStackTrace` / `StackWalker` 给不出帧，死锁只能看监视器图。**这是必须补的部件** |
| `Condition.await/signal` | AQS 家族的这一条还挂（`ReentrantLock`/`CountDownLatch`/`Semaphore` 已通） |
| `drawString` / AWT 真窗口 | JDK 25 的字体栈走 HarfBuzz/FFM；窗口代码写了但起不来 |
| FFM（`java.lang.foreign`）/ `Continuation` | 明确抛 UOE |
| 内存映射文件（`map0`/`transferTo0`） | 明确抛 `IOException` |
| 句柄复用 | 句柄是 `i32` 且四段语义已占满，要复用必须改宽成 `i64 = index32 + epoch32` |
