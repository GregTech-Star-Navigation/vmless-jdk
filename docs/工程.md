## 构建

```bash
cd repo/rustjavac
export PATH="$PATH:/c/Users/Administrator/.cargo/bin"
export CARGO_TARGET_DIR='D:\vmless\rt_xxx'      # 每次换新的，原因见「坑」
cargo build --release --bins --examples
```

产物：

| 文件 | 是什么 |
| --- | --- |
| `$TARGET/release/rustjava.exe` | 解释器（`-cp` / `-jar` / 单文件三种入口） |
| `$TARGET/release/examples/compile_src.exe` | 单文件编译：`compile_src <in.java> <outDir>` |
| `$TARGET/release/examples/run_jit.exe` | JIT 执行 |
| `$TARGET/release/examples/run_jdk.exe` | 带 `java.base` 的真字节码执行：`run_jdk <类目录> <主类名>` |

工具 crate 各自独立构建：

```bash
cd repo/jdk-tools && CARGO_TARGET_DIR=D:/vmless/rt_t_tools cargo build --release --bins
```

## 验收（三道，缺一不可）

### ① 三路一致

```bash
bash /d/vmless/verify.sh <bin目录>
```

`<bin目录>` 里要有 `rustjava.exe` + `compile_src.exe` + `run_jit.exe`。
期望输出：

```
三路一致: 103    失败: 0    缺样例: 0
```

它做的事：106 个样例逐个编译 → 分别用真 `java` / 解释器 / JIT 跑 → **stdout 逐字节 + 退出码**比对。
（`tr -d '\r'` 抹掉 CRLF 差异；空输出会被判失败，防止「跑通了但其实挂了」）

### ② 单元测试

```bash
cd repo/rustjavac && cargo test --release      # 期望 106 passed
```

### ③ GC 压力模式

```bash
VMLESS_GC_STRESS=1 bash /d/vmless/verify.sh <bin目录>    # 期望仍 103/0
```

**这一道不能省**：每次分配都 GC 是漏根的主检出通道。跳过它的代价见 [状态.md 的坑表](状态.md#已知的坑踩过的别再踩)。

### ④ 编译率测量

```bash
examples/cover_dir.exe 'D:/vmless/jbsrc/java.base' 'D:/vmless/patch/img/java.base' \
    --md rustjavac/docs/java-base-失败分布.md
```

**必须带 classpath** —— 不带只有 22%，带了 60%+。跨编译单元的类解析全靠它。

## 发布

```bash
bash packaging/build.sh                  # 全量：build + zip + 安装包 + SHA256SUMS + release notes
bash packaging/build.sh -SkipBuild       # 只重打包
bash packaging/build.sh -SkipBuild -SkipInstaller
```

两个工作流：

| 文件 | 触发 |
| --- | --- |
| `.github/workflows/ci.yml` | push（master/main）、PR、手动。跑两边 `cargo test` + `verify-samples.sh`（默认 20 样例，手动可 `--all`），另有 packaging-smoke job |
| `.github/workflows/release.yml` | push tag `v*`（或手动传版本），构建并上传产物 |

## 事实源与命令的对应

文档里每个数字都要能指到一条命令：

| 数字 | 命令 |
| --- | --- |
| 三路一致 103/103 | `bash verify.sh <bin>` |
| 106 passed | `cargo test --release` |
| java.base 73.9% | `cover_dir` 的汇总行 |
| 解释器 200/202、JIT 197/202 | `grep -oE '^\s+0x[0-9a-f]{2}' src/vm/exec.rs \| wc -l`（同理 translate.rs） |
| native 约 800 条 | `grep -cE 'r\.add\(\|r\.add_override\(' src/vm/nat_*.rs` |
| 109,852 行 Rust | `find */src -name '*.rs' \| xargs wc -l` |
| 39 个工具 exe | `ls /d/vmless/btools/*.exe \| wc -l` |
| 性能表 | `jdkms/par/out/{P1,P2}.class` 两边互跑，多次取中位 |

## 坑

| 症状 | 原因 / 对策 |
| --- | --- |
| `LNK1104` / `Device or resource busy` | 带外文件监视器锁住刚跑过的 exe。**覆盖会静默失败** —— `cp` 报错但你后面跑的还是旧 exe。对策：每轮把产物复制到新目录再跑，`CARGO_TARGET_DIR` 准备两三个轮换 |
| 构建失败但报错在别人的文件 | 多条并行线在改同一个树。看 `src/vm/*.rs` 的 mtime 是否晚于自己最后一次成功构建；不是自己弄坏的不要去改 |
| 通过率突然掉一大截 | `cover_dir` 的 `platform()` 整个进程只反解一次 classpath，一个 `.class` 读失败就静默当「类不存在」→ **先重跑**（实测过 40.8% vs 真值 62.0%） |
| `verify.sh` 全绿但真程序挂 | 那 103 个样例只用 ASCII 路径、不建线程、不用原子类。**真程序路径要单独验** |
| 编译成功但 class 是坏的 | 用 `javap -p -c` 解析 + `-Xverify:all -Xbootclasspath/a:<我们的输出>` 跑真 JVM 对照 |
