# 设计

> 为什么这么设计、否决了哪些方案。跨需求的架构取舍写这里；
> 「数据怎么流动」在 [架构.md](架构.md)，「现在做到哪」在 [状态.md](状态.md)。

## 1. 类库：执行 OpenJDK 自己的 `.class`，不重写

**否决的方案**：自己实现 `java.base`。

`java.base` 有 7350 个类、60 万行 Java。重写它等于重写整个 JDK 的库层，
而这一层的价值不在「你写过」，在「它对」—— 任何一处语义偏差都会让上层库连锁崩。

**选择的方案**：自研 VM 执行 OpenJDK 编好的字节码。
代价是要实现全部 748 个 `native` 方法 + JNI + 类加载 + JPMS；收益是库层语义天然对齐。

判据：`VMLESS_JDK` 指 `lib/modules`，`String.hashCode("hello")` = `99162322`、
`ArrayList`/`HashMap` 零新增 native —— 说明真的在跑 OpenJDK 的字节码，不是替身。

## 2. 两个执行引擎都留着

**否决的方案**：只留 JIT（或只留解释器）。

只有 JIT：JIT 编不了的方法（`wide`、旧 `jsr/ret`、indy 的某些形态）整程序作废。
只有解释器：慢 96.9×，且没有第二个实现来暴露「看起来对」的错。

**选择的方案**：解释器 + JIT 并存，**JIT 按方法回退**到解释器。
两者共享 `Slot` 值模型与局部变量槽布局，所以能互相调用。

副产品是验收手段：HotSpot / 解释器 / JIT **三路逐字节比对**。
多个 bug 就是这样露出来的（`iload_0` 短形式没平移、`lcmp` 翻成 7 条指令、
`get_mem` 符号扩展 —— 都是「两边不一致」先暴露）。

## 3. GC：精确位图，不走保守扫描

**否决的方案**：保守栈扫描（扫栈上每个字，看着像指针就当指针）。

保守扫描实现简单，但整数会被误当引用 → 该回收的回收不了、不该留的留着，
而且**漏根方向无法证明**。

**选择的方案**：**字节码数据流分析**出来的精确引用位图
（等价 verifier 的 ref/prims 分析：每条指令按自己语义弹/压抽象值，跳转点取并集）。
实测 99 个样例：**精确 846,235 槽 / 保守 32,771（96.3% 精确），位图失配 0**。

不认识的形态（`jsr/ret`、`wide`、分析冲突）**退化成整个方法保守** —— 只多留垃圾、不漏根。

## 4. 句柄不复用（宁可 RSS 高，不可回收错）

**否决的方案**：句柄复用（对象死了就把下标还回去）。

句柄是页表下标，一旦复用，**陈旧句柄会静默指向另一个对象** —— 那不是崩溃，是算错。

**选择的方案**：索引不复用，对象死了槽位永久空着。代价是每对象 8 字节页表 + 上限。
现状的陈旧句柄读出来是 `null`，是安全的那一侧。

**已知天花板的诚实记录**：句柄是 `i32` 且四段语义（`>0` 对象 / `<0` 数组 / `0` null /
`>= 1<<24` 字符串）已占满，**第 1677 万个对象会落进字符串段**。
已在分配路径按句柄上限拦成 `None`（走 OOM），不是静默错乱。
要真正解决必须把句柄改宽成 `i64 = index32 + epoch32`，那会碰到 JIT/解释器/全部 native。

## 5. native 层按领域分文件，不集中

**否决的方案**：一个 `native_reg.rs` 放全部 800 条注册。

并行开发时那是战场 —— 每条工作线都改同一个文件，冲突不断，而且一次改坏整仓编不过。

**选择的方案**：`nat_intrinsics` / `nat_os` / `nat_util` / `nat_nio` / `nat_misc` / `nat_desktop`
六个文件各自 `register(r)`，`register_all` 末尾各调一次。

配套的一条铁律：**方法在 OpenJDK 源码里带 `native` 吗**？带 → 进 native 表；
不带 → 它有字节码，就该由解释器执行，**不许在这里写第二份实现**（否则两份实现会漂移）。

## 6. 两套「假地址空间」必须统一

踩过的坑：`nat_intrinsics` 与 `nat_util` 各自造了一套 native 内存模拟（`BTreeMap` 记假地址）。
两边单独看都对，合起来 `nat_os` 读不到也写不进 —— `sun.nio.*` 的 90 多个 native 全废。

**结论**：跨模块共享的东西必须有**唯一实现**（`nat_mem.rs`），不能让两个子代理「各自都对」。
同理适用于「同一条链上的两个组件」：合起来能跑才算对。

## 7. `java.desktop`：接管 `GraphicsPrimitiveMgr`，不实现 loops 注册表

真 JDK 的 `sun.java2d.loops` 是上千个函数指针的注册表（每个 `Blit` 变体一个）。
照着实现不现实，而且没有验证手段。

**选择的方案**：接管 `GraphicsPrimitiveMgr.register`，让 `Graphics2D` 的操作
直接落到我们自己的光栅化器。判据是**逐像素 SHA256 相同**，不是「看起来像」。

实测 `Img1n` diff 0/20000、`Img3`（ARGB 三层 SrcOver）diff 0/19200。

**`drawString` 明确降级**：JDK 25 走 HarfBuzz/FFM，到不了 `DrawGlyphList`。
计划用内置点阵字体 —— 但**它的渲染结果不会与 HotSpot 逐像素一致**（字体与 hinting 不同），
判据只能是「字能正确显示、位置对、颜色对」。不用「逐像素」掩盖做不到的目标。

## 8. 验证优先于实现

几条硬规矩，都是踩出来的：

1. **每完成一块就三路比对**（`verify.sh`），不看「没崩」看「逐字节相同」
2. **`VMLESS_GC_STRESS=1` 必跑** —— 那是漏根的主检出通道
3. **产出 class 要用 `javap` + 真 JVM `-Xverify:all` 对照** —— 「编过了」可能是坏 class
   （实测：12 个编过的文件里 1 个真 JVM 拒载）
4. **先做判别实验再优化** —— 本轮最大的一个教训：任务书写「JIT 内联有分支的被调方」，
   实测把循环体手工内联进 main 后 **0 收益**（只省 4 条 call），真正瓶颈是 `lcmp` 被翻成 7 条指令
5. **测量错误比代码 bug 更危险** —— `cover_dir` 的 `platform()` 一次 `.class` 读失败就静默当
   「类不存在」，一次污染整轮 3000 个文件（40.8% vs 真值 62.0%）。看到数字突变先重跑
