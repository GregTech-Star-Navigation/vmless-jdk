# GC：解释器堆的标记-清扫回收（2026-11-18）

状态：可用（v0.58 之后的一次能力补充）。文件：`src/vm/gc.rs`（主体）、
`src/vm/shared.rs`（堆结构 / 标记位 / 清扫）、`src/vm/frame.rs`（帧带位图）`、
`src/vm/exec.rs`（接入点）。

## 一句话

解释器的对象堆原来**只增不减**（线性于累计分配量）。现在接上了**精确根**的标记-清扫：
8M 次分配 / 100 万存活的负载下，最大停顿 **12.5–13.6 ms**（G1 实测 12.74 ms），
2M 个短命对象下峰值 RSS 从 297 MB 降到 62 MB。

## 为什么是「标记-清扫 + 不搬动」

句柄就是页表下标（`>0` 对象 / `<0` 数组 / `>= STR_BASE` 字符串），页表里已发布的条目
**地址永不搬动** —— 这是「任何线程都能安全拿任意对象引用」的全部前提。搬动会让所有
句柄失效，所以：

- **不压缩**（要压缩得先做出句柄间接层，那是另一件事）；
- **索引不复用**：复用会让「还活在别处的陈旧句柄」指向另一台对象 —— 静默数据损坏，
  比多占一点页表内存糟得多。代价是累计分配量有个 3355 万的上限（页表用尽时报
  `OutOfMemoryError`，与改动前一样）。

## 精确根从哪来（这是整件事的拦路虎）

`Frame.locals` 是 `Vec<Slot>`，引用（句柄 i32）和 int 混在一起没有类型标签。追溯扫描
无法区分「句柄 5」和「整数 5」：把整数当引用 → 把随机下标当对象；漏掉真引用 → 活对象
被回收。所以每个方法在**第一次执行时**算一张 `pc → (哪些局部槽是引用, 哪些栈位是引用)`
的表（`gc::MethodRefs`），运行期帧带着它（`Frame.refs` + `Frame.pc`）。

- **来源**：字节码**数据流分析**（`gc::analyze`）—— 等价 JVM 校验器做的事，只是格简化成
  「引用 / 非引用 + 槽宽」：`aload` 压引用、`iload` 压 int、`invoke*` 看返回描述符、
  `getfield` 看字段描述符……跳转点用**并（OR）**合并（并 = 往「多标」方向走，安全）。
  比 `StackMapTable` 更细：`StackMapTable` 只在分支目标/异常入口给帧，这里**每条指令
  都有**。异常 handler 的局部变量取 try 范围内各指令状态的并（过近似，安全）。
- **退化**：不认识/对不上（`jsr/ret/wide`、栈深或宽窄不一致）→ 整个方法用**保守位图**
  （所有槽都当潜在引用，逐个用页表验证）。保守只会多留垃圾，不会漏根。
- 缓存在 `Shared.refmaps`（键是 `(Arc<ClassFile> 指针, 方法下标)`，连 `Arc<ClassFile>`
  一起存，指针不会被复用）。

**运行期兜底**（宁可漏回收，不能回收错）：

1. 帧的位图与当前栈深对不上 → 这一帧退回保守扫描（实际栈比位图短是合法的：停在调用点
   上时参数已经弹掉，剩下的正好是位图栈的前缀）。
2. **Rust 栈保守扫描**：解释器/native/反射/indy 在 Rust 局部变量里临时拿着一句柄的情况
   （异常对象在展开途中、indy 的临时值）靠它兜住。候选值一律过页表验证。
3. 共享冷表（静态字段、类对象表、字符串常量表、indy 状态、监视器表、线程表、包装类缓存…）
   按「表里出现的 i32 都可能是句柄」处理并验证 —— 表都很小，多标有界。
4. 每个线程的 `Vm.held`（持有但未膨胀的 thin 锁对象句柄）。

## 回收协议

- **只在解释器主循环的指令边界上回收**：`pc` 精确、栈形状与位图一致。分配函数自己
  **不**触发回收，只累加计数（否则 `pc` 会停在半条指令上，位图对不上）。
- 停世界沿用 `gc.rs` 原有的停靠点协议；**停不全就放弃这一轮**（4 ms 超时，失败后 50 ms
  内不再尝试）。每个线程各自宣告「我停在第几轮」，所以上一轮迟到的宣告不会被下一轮
  误当成「已到齐」。
- 标记：世代号 + 工作队列，**多线程**（默认 `min(核数, 8)`，`VMLESS_GC_THREADS` 可覆盖）。
  分配在 GC 期间发生的对象直接带「本轮已标记」的世代号。
- 清扫：**在暂停之外**做（就地做小堆，起后台线程做大堆）。清扫只释放「世代号 < 本轮」
  的条目，所以和新一轮标记不会打架（新标记会把活对象的世代号写到更新，清扫条件不成立）。
- 触发：`已分配数 >= max(存活数 × 2, 262144)`。

## 开关（都是环境变量）

| 变量 | 作用 |
| --- | --- |
| `VMLESS_GC_STATS=1` | 每次回收打一行：pause / live / 位图覆盖率；清扫另打一行 |
| `VMLESS_GC_STRESS=1` | 压力模式：每 64 条字节码检查一次，**只要这一小段分配过就回收**（把漏根立刻打成崩溃）。合并后用它复跑回归 |
| `VMLESS_GC_OFF=1` | 完全关掉回收（量「改前」基线用，其余行为不变） |
| `VMLESS_GC_VERIFY=1` | 每轮打印「精确 / 保守 / 位图失配」帧数 |
| `VMLESS_GC_THREADS=N` | 标记线程数 |
| `VMLESS_REFMAP_DEBUG=1` | 位图退化时打印原因（pc + 指令） |

## 已知边界（没做的）

- **索引不复用**（见上）：RSS 里仍有一项随累计分配量线性增长 —— 页表条目 8 字节/对象
  （1M/2M/4M 次分配实测 51/62/82 MB）。要彻底平，得做「空闲表 + 显式失效」或者句柄
  间接层。
- **没有增量/并发标记**：标记仍然是 stop-the-world，pause ∝ 存活对象数。
- 字符串堆（`STR_BASE` 以上的句柄）**不回收**：它们是不可变常量/驻留串。
- `exc_msgs` 等冷表会把异常对象一直留到表项被覆盖（改动前就有的行为）。
- 页表是按对象**下标**组织的一级/二级结构，标记每个对象至少一次页表查找 + 一次
  `ObjHdr` 访问；`ObjHdr.refs` 为 `None` 的对象跳过槽位数组（不碰第二次缓存行）是
  把停顿从 15.7 ms 压到 12.6 ms 的关键优化。
