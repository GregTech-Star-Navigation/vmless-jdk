# 线程与对象监视器（实现说明）

> 状态：已完成 · 2026-11-17 · 对应 REQ-002
> 代码：`src/vm/thread.rs`（主体）、`src/vm/exec.rs`（指令 + 抢占点 + `ACC_SYNCHRONIZED`）、
> `src/vm/native_reg.rs`（native + 接管表）、`src/vm/class.rs`（`<clinit>` 串行化）

## 一句话

Java 线程 = OS 线程；**整个 `Vm` 一把锁（GIL）**，谁持锁谁独占访问；阻塞点显式交还 GIL。
监视器是 GIL 下的一张普通表 —— 于是「堆要不要加锁」这个问题不存在。

## 为什么是 GIL，而不是 `Arc<Mutex<Heap>>`

解释器（`Vm`）从头到尾是 `&mut self`：对象堆、静态字段、类表、字符串池、常量池缓存都在里面。
把堆拆出去意味着把 `execute` 里几千处 `self.objects[…]` 改成「先 lock 再访问」，而且**阻塞点**
（`sleep` / `wait` / `join` / 等锁）上 `&mut self` 还要能交还 guard —— Rust 的借用检查不允许。

所以换成等价但可行的做法：

- 一把 **票据锁**（ticket lock，FIFO）当 GIL；
- `Vm` 的地址放 `AtomicPtr`，**持锁时**才解引用成 `&mut Vm`
  （整个模块唯一的 unsafe 约定，集中在 `vm/thread.rs` 的 `vm_ref`）；
- 阻塞点 `gil_unlock()` → park → `gil_lock()`。

代价：Java 线程之间**不并行**执行字节码（等价于 CPython 的 GIL）。
收益：没有任何数据竞争，不需要 TLAB、不需要对象搬动时的锁、不需要 split heap。

> 为什么不是普通 `Mutex` 而是票据锁：`safepoint` 上的模式是「释放后立刻重抢」。
> 非公平锁下同一个线程会一直赢，别的线程永远跑不上来 —— 那不是「偶发慢」，是**饿死**。

## 线程模型

```
main ── gil_lock ──> 解释器（帧栈在 main 的 Rust 栈上）
  └─ Thread.start() ──> std::thread::spawn ──> set_tid ──> gil_lock ──> run() ──> 收尾
```

- **每个 Java 线程一个帧栈**是白拿的：解释器的 `Frame` 就是这个线程的 Rust 栈上的局部变量。
- **抢占**：解释器主循环每 `SAFEPOINT_EVERY = 512` 条字节码 `gil_unlock/gil_lock` 一次。
  没有它，一个 `while(true){}` 线程会让别的线程永远跑不上来（`Thread.start` 之后对方起不来）。
  单线程时退化成一次整数比较（`nthreads <= 1` 直接 return）。
- **主线程退出**：`run_main` 结束前 `wait_non_daemon()`，等所有非 daemon 线程跑完；
  `System.exit` 走 `Shutdown.halt0` → 刷 `Vm::output` 后 `process::exit`（不等、也不丢输出）。

## 监视器

```rust
struct Monitor { owner: u64, count: u32, entry: VecDeque<u64>, cond: VecDeque<u64> }
```

| 操作 | 语义 |
| --- | --- |
| `monitorenter` | 空闲 → 拿锁 count=1；自己持有 → count+1；别人持有 → 进 `entry` 队列 park（**不响应中断**，JVMS 如此） |
| `monitorexit` | count-1；归零时**移交**给 `entry` 队首（hand-off，堵住插队窗口）并 unpark 它 |
| `wait` | 必须持锁（否则 `IllegalMonitorStateException`）；**完整释放**（重入计数记下来）→ 进 `cond` → park；醒来后重新获取锁、计数还原 |
| `notify/notifyAll` | 必须持锁；把 `cond` 队首（或全部）搬进 `entry`，owner 空闲时立刻移交 |

单据化的是「醒来的是谁」：因为只有 GIL 持有者在跑，队列操作与状态判定都在同一临界区里，
不存在「醒来后状态又变了」的窗口 —— 除了一个明确处理的分支：`park` 返回后必须**重新判定**
（被移交了？还在队列里？超时？中断？），这也是 `Object.wait` 里那个 `loop` 的全部内容。

## `synchronized` 方法与块

- **块**：`0xc2/0xc3` 两条指令直接在解释器里做。异常要**先过本方法的异常表** ——
  javac 给 `synchronized` 块生成的 `monitorexit` 就在 handler 里；这一步没做对，
  异常路径上的锁永远不释放（`local_handler` 就是干这个的）。
- **方法**（`ACC_SYNCHRONIZED`）：加解锁放在 `execute` 这一层，因为**每个**调用点
  （virtual/special/static/interface/indy/lambda）最终都走它，放这里不会漏；异常路径同样解锁。
  实例方法锁 `this`，静态方法锁**声明类**的类对象（`class_obj` 保证同一个类永远同一个句柄）。

## `Thread` 的接管点

`Thread.<init>` / `Thread.start()` 是 **VM 接管**（`NativeRegistry::overrides`），其余全走真字节码：

| 走真字节码 | 由 VM 提供 |
| --- | --- |
| `run`（虚分派到子类）、`join`（`synchronized(this){ while(isAlive()) wait() }`）、`getState`、`isAlive`、`getName`、`setDaemon`、`interrupt`（Java 包装）、`sleep(long)` 的参数检查 | `Thread.<init>` ×9、`Thread.start()`、`currentThread`、`sleepNanos0`、`interrupt0`、`holdsLock`、`yield0`、`<clinit>` 里的 `registerNatives` |

为什么必须接管构造器：真构造器要 `ThreadGroup` → `ClassLoader.getSystemClassLoader()` →
`ServiceLoader` 一整条链，那条链对「建一个线程」没有任何意义。
接管后 `Thread` 的字段布局照样是真的（`holder`(FieldHolder) / `name` / `eetop` /
`interruptLock` / `tid`），所以 `getState`/`isAlive`/`setDaemon` 的**真字节码**原样工作。

字段口径（踩过两次，记牢）：

- `getState()` → `holder.threadStatus`（HotSpot JVMTI 位）；**等待态不能带 RUNNABLE 位**
  （`VM.toThreadState` 先判 bit `0x4`）；
- `isAlive()` → `eetop != 0`；
- `daemon` / `priority` 在 **`Thread$FieldHolder`** 上，不在 `Thread` 对象上；
- 中断有两份状态：Rust 镜像 + `Thread.interrupted` 字段，**投递异常时一起清**。

## 内存可见性（D）

- 每次 `gil_unlock`/`gil_lock` 都是互斥锁的 release/acquire，本身就是**全屏障**；
  于是「线程 A 的写对线程 B 立即可见」在字节码边界上成立（不存在两个线程同时读写的窗口）。
- `Unsafe.getXVolatile` / `putXVolatile`（int/long/reference）与五个 `*Fence` 额外加了
  `fence(SeqCst)` —— 显式的编译器屏障，不靠「反正单线程」的隐式结论。
- 普通（非 volatile）读写：本 VM 不做 JMM 的重排语义建模，靠上面的屏障保证不会读到陈旧值；
  真要弱内存序的精确行为，需要 per-field 的屏障而不是 VM 级屏障 —— 明确记为不做。

## 死锁检测

`Vm::debug_threads()`（`tid / name / state / daemon / 持有的锁 / 在等谁`）+
`Vm::debug_deadlocks()`（在「持有-等待」图上找环，自环不算）。
watchdog 线程每 250ms 看一次：连续 4 次「所有存活线程都不在 RUNNABLE」**且**图上有环，
就按 `jstack -l` 的格式打报告并 `exit(1)`。`VMLESS_NO_DEADLOCK_REPORT=1` 关掉
（关掉后与 HotSpot 一致：进程挂着等人 attach）。`VMLESS_THREAD_DUMP_MS=1` 每 tick 打一次
线程表，排查挂起用。

帧列表没有：本 VM 没有调用栈模型（`Throwable.getStackTraceDepth()` 恒 0）。

## 边界

- JIT：遇到 `monitorenter`/`monitorexit`/`ACC_SYNCHRONIZED` 方法**明确报错**，
  `run_jit` 整体退回解释器（`examples/run_jit.rs` 的降级判据里加了这三条）。
- 虚拟线程不支持（`isVirtual()` 恒 false，`Thread.ofVirtual()` 会走到未实现的 native）。
- `ThreadGroup` 不做：`getThreadGroup()` 返回 null。
- 我们的编译器（`src/codegen`）对 `synchronized` 仍是「解析后丢弃」，那是编译器侧的缺口。
