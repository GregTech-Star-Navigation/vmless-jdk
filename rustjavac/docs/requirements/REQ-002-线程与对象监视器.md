> 状态：已完成 · 2026-11-17

> 设计说明：`docs/线程与监视器.md`

## 1. 要做什么

让解释器能跑**真的并发 Java**：`java.lang.Thread`、`monitorenter`/`monitorexit`、
`synchronized` 方法/块、`wait`/`notify`/`notifyAll`、线程状态、`sleep`/`join`/`interrupt`、
daemon 语义。这是「跑 Minecraft」剩下的最后两条字节码（195/202 → 197/202）。

四条线，按顺序：

- **A 对象监视器**：可重入；被别的线程持有就阻塞；计数下溢抛 `IllegalMonitorStateException`；
  `ACC_SYNCHRONIZED` 方法自动加解锁（实例锁 `this`、静态锁类对象）；JIT 侧**明确报错并整体
  退回解释器**（不许静默不加锁）。
- **B 线程**：每个 Java 线程 = 一个 OS 线程，各自的帧栈；`Thread.start0/currentThread/
  isAlive/join/sleep/interrupt/isInterrupted/getState`；堆多线程共享；状态真反映在
  `getState()` 上；`join` 真阻塞；主线程退出要等非 daemon 线程（`System.exit` 除外）。
- **C `wait`/`notify`/`notifyAll`**：条件队列挂在监视器上；不持锁调用 → 异常；带超时。
- **D 内存可见性**：volatile 语义要成立（至少编译器屏障），普通读写给出明确说法。

## 2. 不做什么

- **不并行执行字节码**：实现是「一把大锁（GIL）+ 线程切换」，不是多核并行。理由与代价见设计文档；
- **不拆 `Heap` 成 `Arc<Mutex<Heap>>`**：`Vm` 是 `&mut self` 到底的结构，拆堆等于重写解释器；
  GIL 在语义上等价（加锁粒度 = 整个 VM），且不需要 TLAB / 搬动时的锁；
- **不接 `librustjrt` 的 `SharedHeap`**：那是 JIT 侧的堆，解释器用自己的堆，两者不混；
- **不做 JIT 侧的监视器**：JIT 遇到 `monitorenter`/`monitorexit` 或 `ACC_SYNCHRONIZED` 方法
  明确报错，`run_jit` 整体退回解释器；
- **不做虚拟线程**（`Thread.ofVirtual` / `VirtualThread`）：`isVirtual()` 恒 false；
- **不做 `ThreadGroup`**：`Thread` 构造器由 VM 接管（groupId 留 null），真走 `ThreadGroup`
  会把 `ClassLoader.getSystemClassLoader()` 整条链拖进来；
- **不做调用栈模型**：`Thread.getStackTrace()` / `Throwable.getStackTrace()` 仍是空，
  所以 `jstack` 的帧列表没有（锁图是完整的）；
- **不改其它子代理目录**（`repo/`、`dllwork/`、`jdk-*/`、`merge/`、`jbcov/`、`jdkapi/`），
  也没接 `vmless_attach`（那是 `jdk-attach` 的活）。

## 3. 已知约束

- **`getState()` 读的是 `Thread.holder.threadStatus`**（java.base 真字节码：
  `getState → threadState → holder.threadStatus → VM.toThreadState(int)`），
  所以写进去的必须是 HotSpot 的 JVMTI 位，而且**等待态不能带 RUNNABLE 位**
  （`toThreadState` 先判 bit 0x4；带了就一律报 RUNNABLE —— 踩过）；
- **`isAlive()` 读 `eetop != 0`**，`daemon`/`priority` 在 `Thread$FieldHolder` 上，
  **不在 Thread 对象上**（拿 Thread 去按 FieldHolder 的字段名读会读到别的字段 —— 踩过）；
- `Thread.<init>` / `Thread.start()` 由 VM 接管（HotSpot 里它们本来就是 VM/native 语义），
  其余全走真字节码 —— 于是 `join` 就是 `synchronized(this){ while(isAlive()) wait() }`，
  线程终止必须 `notifyAll(thread 对象)`，否则 `join` 永远不醒；
- **`<clinit>` 必须串行化**（JVMS 5.5）：一个类同时只能一个线程初始化，别的线程要阻塞等。
  多线程下不这么做的后果很具体：`<clinit>` 跑到一半让出 GIL，别的线程 `getstatic` 读到
  默认值 0（`TimeUnit.MILLISECONDS` 变 null → `Thread.sleep` 里 null 取字段 → 操作数栈下溢）；
- `Thread.sleep` 全族落到 `sleepNanos0`，`wait` 落到 `wait0(J)`，`interrupt0`/`clearInterruptEvent`/
  `holdsLock` 都在 native 表里；中断标志有**两份**（Rust 镜像 + `Thread.interrupted` 字段），
  投递异常时必须一起清；
- `Unsafe.park/unpark` 现在是**真阻塞**（`LockSupport`/AQS 的底座），允许伪唤醒，
  无限期 park 用 100ms 时间片轮转（丢了 unpark 也不会永久挂死）。

## 4. 方案（要点）

1. **GIL**：`static GIL: Mutex<Gil>` 是**票据锁**（FIFO）；`Vm` 的地址放在 `AtomicPtr`，
   持锁时才能取 `&mut Vm`（唯一 unsafe 约定，集中在 `vm/thread.rs`）。
2. **线程 = OS 线程**：`std::thread::spawn`，闭包里 `set_tid → gil_lock → 跑 run() → 收尾`；
   帧栈就是那个线程的 Rust 栈（「每线程一个帧栈」白拿）。
3. **抢占点**：解释器主循环每 `SAFEPOINT_EVERY=512` 条字节码 `gil_unlock/gil_lock` 一次，
   否则死循环线程会把别的线程饿死；单线程时只是一次整数比较。
4. **监视器**：`monitors: 句柄 → {owner, count, entry, cond}`；`monitorexit` 归零时**移交**
   给 entry 队首（防插队）；`wait` 完全释放（含重入计数）→ 进 cond 队列 → 被 notify 搬进
   entry → 重新获取 → 计数还原。
5. **`ACC_SYNCHRONIZED` 放在 `execute` 这一层**：所有调用点（virtual/special/static/
   interface/indy/lambda）都经过它，不会漏；异常路径也解锁。
6. **VM 接管表**（`NativeRegistry::overrides`）：`Thread.<init>` ×9 / `Thread.start()`，
   在执行字节码**之前**拦截，热路径上用「类名不分配比较」挡住。
7. **死锁报告**：watchdog 线程每 250ms 检查一次「所有存活线程都不在 RUNNABLE 且等待图有环」，
   命中就按 `jstack -l` 的格式打到 stderr 并 `exit(1)`（`VMLESS_NO_DEADLOCK_REPORT=1` 可关）。

## 6. 不做 / 没做到的

- JIT 的监视器：没做（明确报错 + 整体退回解释器，已按任务要求）；
- `jstack -l` 的**帧列表**：本 VM 没有调用栈模型，只有锁图；
- 接 `vmless_attach`（`jdk-attach` 的 `threads()`）：属于该 crate，未动（约定见下文）
  —— 需要的形状就是 `Vm::debug_threads()` 给出的那五列
  （`tid / name / state / daemon / 持有的锁 / 在等谁`）+ `Vm::debug_deadlocks()` 的环。
- 我们自己的编译器（`src/codegen`）对 `synchronized` 仍然是**解析后丢弃**（不生成
  monitorenter）—— 那是编译器侧的活，本 REQ 只覆盖 VM 侧；真 javac 字节码已完整支持。
