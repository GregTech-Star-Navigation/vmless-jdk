# vmless vs HotSpot 25 —— 基准报告

> 生成时间：2026-11-17T17:29:56.538Z　·　脚本：`bench/run.sh`（重跑同一条命令复现）
> 原始数据：`bench/raw/*.jsonl`（每次运行一行）与 `bench/logs/*.log`（子进程输出）

机器：36 逻辑核 / 64GB RAM / Windows。**注意**：跑这份基准时机器上还有别的编译任务在跑，
且每次创建进程都会被带外扫描器检查一遍 —— 两者都体现在「进程创建底噪」这一行里。
本机进程创建底噪（`hostname.exe`，min）：**136.8 ms**。所有墙钟对比都受它影响，
所以下面凡是有墙钟的地方都同时给出 min（受噪声最小）与 median。

## 1 启动时间

30 次/项交错跑，取 min 与 median。`扣底噪` = min − 进程创建底噪，代表运行时自己花的钱。

| 用例 | min ms | median ms | 扣底噪 ms | 峰值 RSS |
| --- | ---: | ---: | ---: | ---: |
| HotSpot `java -version` | 485.6 | 1061.1 | 348.9 | 42.6 MB |
| HotSpot 空 main | 727.3 | 1126.1 | 590.6 | 42.7 MB |
| HotSpot HelloWorld | 537.0 | 1122.2 | 400.2 | 18.4 MB |
| HotSpot 1000 行类 | 498.6 | 1141.6 | 361.8 | 42.9 MB |
| vmless `rustjava` 空 main（内建 java.base 子集） | 137.9 | 259.2 | 1.2 | 4.8 MB |
| vmless `rustjava` HelloWorld | 110.9 | 259.0 | -25.8 | 4.9 MB |
| vmless `rustjava` 1000 行类 | 106.1 | 272.3 | -30.7 | 5.0 MB |
| vmless `run_jit` 空 main | 133.9 | 299.5 | -2.9 | 5.5 MB |
| vmless `run_jit` HelloWorld | 146.4 | 310.1 | 9.7 | 5.6 MB |
| vmless `run_jit` 1000 行类 | 146.5 | 313.9 | 9.8 | 5.9 MB |
| vmless `run_jdk` 空 main（真 java.base 5421 类） | 2405.1 | 3828.6 | 2268.4 | 111.3 MB |

- 空 main：vmless `run_jit` 133.9 ms vs HotSpot 727.3 ms → **vmless 快 5.43×**
- 空 main：vmless `rustjava` 137.9 ms → **vmless 快 5.27×**
- 扣掉相同的底噪后差距更大：`run_jit` -2.9 ms vs HotSpot 590.6 ms（5.43× / 5.27×）。
- `rustjava` 的 min 已经贴着底噪（有时低于它，说明那几次扫描器没介入）——**即运行时自身开销低于本机测量分辨力**。
- 反过来，`run_jdk`（要解析真 java.base 模块镜像、eager 装 5421 个类）是 **3.5 s 级**，比 HotSpot 慢一个数量级 —— 见 §6。

## 2 内存占用

### 2.1 峰值 RSS

| 场景 | HotSpot 峰值 RSS | vmless 峰值 RSS | 谁省 |
| --- | ---: | ---: | --- |
| 空 main（常驻） | 42.7 MB | 5.5 MB | **vmless 省 7.76×** |
| 空 main（rustjava） | 42.7 MB | 4.8 MB | **vmless 省 8.81×** |
| 8M 次分配、全部即死 | 50.7 MB | 133.5 MB | HotSpot 省 2.63× |

### 2.2 对象大小

对象大小按**布局公式**给（这是权威值，两边都能从各自的源码/文档推出），RSS 斜率只当交叉验证：

| 对象形状 | vmless | HotSpot 25 | 差 | 依据 |
| --- | ---: | ---: | ---: | --- |
| 空对象 `class E {}` | **8 B** | **16 B** | vmless 小 2× | 我们 `HEADER=8`（`class_id u32 + flags u32`），HotSpot 12 B 头 + 4 B 对齐填充 |
| `{int v; long pad1}` | **24 B** | **24 B** | 打平 | 我们 = align8(8 + 3 槽×4)=24；HotSpot = 12 头 + 4 int + 8 long = 24 |
| 引用数组每槽 | **4 B** | 4 B（压缩 oops） | 打平 | 我们存 `u32` 堆内偏移，HotSpot 压到 32 位引用 |

RSS 斜率交叉验证（保持 100 万 / 400 万 个 `ONode{int,long}` 存活，取峰值 RSS 差）：

| 存活对象数 | HotSpot 峰值 RSS | vmless 峰值 RSS |
| ---: | ---: | ---: |
| 1M | 70.5 MB | 32.5 MB |
| 2M | 148.2 MB | 133.5 MB |
| 4M | 158.1 MB | 135.6 MB |
| 8M | 262.8 MB | 267.1 MB |

- HotSpot 斜率 30.60 B/对象（1M→4M）、28.80 B/对象（1M→8M）：
  ≈ 24 B 对象 + 4 B 数组槽 + TLAB/堆松弛 —— **与 24 B 的布局吻合**。
- vmless 斜率 36.03 B/对象（1M→4M）、35.14 B/对象（1M→8M）：**这个数不可用**，
  因为我们的堆是一整块连续内存按 `realloc` 增长（初始 64 MB、按步进扩容），
  1M/2M 两点经常落在同一个容量台阶上（上表里 2M 和 4M 几乎一样就是台阶），斜率被台阶吃掉。
- 所以这一项的口径是：**空对象 8 B vs 16 B（2×），双字段对象打平（24 B vs 24 B）**。
  任务书里「16 B vs 24 B」指的是不同对象形状，我们赢在对象头，赢不了字段对齐。

## 3 GC 停顿

负载：8,000,000 次分配、1/8（100 万）存活。两边都限制在 256 MB 堆。
HotSpot 用默认 G1（`-Xlog:gc` 解析 Pause 行），vmless 用 `VMLESS_GC_STATS=1` 打印的分代统计。

| 指标 | HotSpot 25 (G1) | vmless (JIT 堆) | 对比 |
| --- | ---: | ---: | --- |
| GC 次数 | 2.0 | 2.0 | — |
| **最大单次停顿** | 12.74 ms | 46.32 ms | HotSpot 小 3.64× |
| **总停顿** | 18.48 ms | 81.17 ms | HotSpot 少 4.39× |
| 程序内耗时（自报） | 73.0 ms | 1872.0 ms | — |
| 峰值 RSS | 175.0 MB | 518.1 MB | — |

- 解释器走同一个程序：程序内 `56978.0` ms、墙钟 `57669.0` ms，
  而且**解释器侧的 GC 没有任何停顿遥测**（`src/vm/gc.rs` 不计 pause）—— 这一行只能标 n/a，是已知短板。
- 我们的 GC 是分代复制 + 老年代标记清扫，堆是一整块连续内存（`realloc` 增长），
  **但实测是我们输**：最大单次停顿 3.6×、总停顿 4×（与「我们停顿更小」的预期相反，照实写）。
  原因：我们是一次性 stop-the-world 的复制式 minor + 老年代标记清扫 major，
  整堆是一块连续内存，major 要遍历/搬运全堆，且没有并发标记，工作全压在单次停顿里；
  G1 用分区 + 并发标记 + 混合回收把同样的工作摊成很多个短停顿。
  另外堆按步进扩容，容量增长也发生在同一次 GC 里，搬运成本一起计入。
  峰值 RSS 同样更高（整块连续堆扩容时会 double），这是「快启动 / 省常驻」换来的代价。

## 6 类加载

| 用例 | 结果 |
| --- | --- |
| HotSpot 加载 5000 个 java.base 类（`Class.forName(name,false,loader)`，程序内自报） | 258.0 ms，成功 5000.0 个，失败 0.0 个 |
| HotSpot 空 main（`-Xshare:off`，冷启不读 CDS 归档） | min 160.3 ms |
| vmless `run_jdk` 启动即装 5421 个 java.base 类 | min 548.5 ms（打印 `类表: 5421.0 个类`） |
| vmless 跑同一个 `ClassLoad2` | **跑不了**：失败 |

- 口径不一样，必须说清：HotSpot 是**惰性加载**（用到才装），vmless 是**启动即 eager 装全量类表**。
  所以「5421 类」这个数对我们是启动成本、对 HotSpot 根本不是它的启动路径 —— 这一项**不能**当成同类比较。
- 我们跑不了 `Class.forName(...)` 那条路，是因为解析 `java.util.concurrent.ConcurrentHashMap` 时会调用
  `jdk.internal.access.JavaLangAccess.currentCarrierThread()`，我们的 java.base 支持面还没有它。
- 结论：**类加载这一维我们没有可比数字，只有「eager 3.5 s」这个成本**。要跟 HotSpot 比，得先做惰性加载或类表归档。

## 7 解释执行吞吐

同一份字节码（`P2j`，8M×4 次循环、无 indy），跑完取程序自报的毫秒数。

| 引擎 | 程序内耗时 | 墙钟 min | 相对 HotSpot |
| --- | ---: | ---: | --- |
| HotSpot 25（C2 编译后） | 73.0 ms | 193.5 ms | 1× |
| vmless 解释器（`run_jdk`） | 7076.0 ms | 7538.7 ms | **慢 96.93×** |
| vmless 解释器跑原始 `P2`（带 indy 字符串拼接） | 7729.0 ms | 8343.7 ms | 慢 105.88× |

- 这个差距是**结构性的、不是 bug**：HotSpot 跑的是 C2 优化后的机器码（循环展开、强度削减、寄存器分配），
  我们是逐条字节码解释（每条指令一次 `match` 分发）。差一到两个数量级是解释器的正常水位。
- 也说明 `P2` 这类纯计算循环是我们最不擅长的形状 —— 没有对象、没有调用、全是热点算术。

## 8 JIT 吞吐

| 用例 | 程序内耗时 | JIT 编译耗时 | 说明 |
| --- | ---: | ---: | --- |
| HotSpot 25 | 73.0 ms | — | C2 |
| vmless JIT（`run_jit`，P2j） | 418.4 ms | 1.7 ms | Cranelift 直出机器码 |
| vmless JIT 跑原始 P2 | 6796.0 ms | — | **回退了解释器**（JIT 不支持 invokedynamic） |

- JIT 对解释器的加速：**16.91×**（7076.0 → 418.4 ms）—— JIT 本身是有效的。
- 但离 HotSpot 还差 **5.73×**：我们只做「静态整方法直译」，
  没有分层编译、没有内联、没有循环优化、没有 PGO。HotSpot 的热点循环会被 C2 反复优化几轮。
- 原始 `P2` 走 JIT 会**整体退回解释器**（原因：JIT 不支持 invokedynamic（0xba@53）：P2.main([Ljava/lang/String;)V 里的 lambda / 字符串拼接只能由解释器执行（JIT 未接入调用点缓存）），
  这是已知设计边界（`rustjavac/examples/run_jit.rs` 里明说了），不是坏掉。
- **口径提醒**：`run_jit` 目前是「一处不支持就**整个程序**退回解释器」
  （`invokedynamic` / `java.lang.invoke` / `synchronized` 三种触发）。这个策略正在改成逐方法回退，
  所以**凡是用到 lambda、字符串拼接、同步块的程序，`run_jit` 的数字都偏低**。
  本文的 JIT 数字取自 `P2j`（刻意避开这三样）；同形状的真字节码路径 `run_jdk` 对照值见上一节。

## 9 并行扩展性

程序形状与 `jdkms/par/P1` 相同：起 N 个线程，**每个线程各做 8M 次循环**（总工作量随 N 增长）。
所以这里的「加速比」按**吞吐**算：`N × t(1) ÷ t(N)` —— 完全并行时它等于 N，等于 1 表示一点没并行。
都用程序自报的内层毫秒数，启动成本不混进来。

| 线程数 | HotSpot 内层 ms | HotSpot 加速比 | vmless 内层 ms | vmless 加速比 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 32.0 | 1.00× | 1860.0 | 1.00× |
| 2 | 42.0 | 1.52× | 1861.0 | 2.00× |
| 4 | 61.0 | 2.10× | 1872.0 | 3.97× |
| 8 | 77.0 | 3.32× | 2089.0 | 7.12× |

- 8 线程吞吐加速比：HotSpot 3.32×、vmless 7.12×（36 核，理论天花板 8×）。
- 我们的解释器已经拆掉 GIL（`rustjavac` 0.57 的「字节码真并行」），所以确实随核数变快；
  但每个线程都是解释执行，绝对耗时仍然比 HotSpot 慢一个数量级 —— **并行度赢了，绝对值没赢**。
- JIT 侧的多线程是**跑不了**的：`run_jit` 对 P1j 报 `JIT 编译失败`。
  这是 JIT 引用分析在 `aaload` 之后的状态建模缺口，属于已知待修项（任务书里 JIT 由另一个子代理负责）。

## 10 汇总：赢在哪、输在哪

### 赢的维度

| 维度 | vmless | HotSpot 25 | 倍数 |
| --- | ---: | ---: | ---: |
| 启动（空 main，min） | 133.9 ms | 727.3 ms | **5.43×** |
| 启动（rustjava，min） | 137.9 ms | 727.3 ms | **5.27×** |
| 常驻 RSS | 5.5 MB | 42.7 MB | **7.76×** |
| 对象大小（空对象） | 8 B | 16 B | **2.00×** |
| 8 线程并行吞吐加速比 | 7.12× | 3.32× | **2.14×** |

> 注：HotSpot 的最小启动本身在 485–727 ms 之间波动（同一台机器上 -version、空 main、HelloWorld 三个用例的 min 都不相同），
> 所以「启动快多少」是个区间：**3.6×–5.4×**，取哪一端取决于拿哪个用例当基准。表里用的是最保守的对手（空 main 的 min）。

### 输的维度

| 维度 | vmless | HotSpot 25 | 倍数 | 为什么 |
| --- | ---: | ---: | ---: | --- |
| 最大单次 GC 停顿 | 46.32 ms | 12.74 ms | 慢 3.64× | STW 复制+标记清扫，整块连续堆、无并发标记；G1 用分区+并发摊平 |
| 总 GC 停顿 | 81.17 ms | 18.48 ms | 慢 4.39× | 同上；另外堆扩容也发生在 GC 里 |
| 分配峰值 RSS（8M 即死对象） | 133.5 MB | 50.7 MB | 慢 2.63× | 整块堆按步进扩容，扩容时 RSS 会翻倍 |
| 解释执行吞吐 | 7076.0 ms | 73.0 ms | 慢 96.93× | 逐条字节码解释 vs C2 编译后的机器码 |
| JIT 吞吐 | 418.4 ms | 73.0 ms | 慢 5.73× | 静态整方法直译，无内联/循环优化/分层 |
| 类加载（可用性） | 跑不了 Class.forName 全量 | 258.0 ms / 5000 类 | — | 缺 jdk.internal.access 面；且 eager 装表更慢 |
| eager 类表启动 | 2405.1 ms | 727.3 ms | 慢 3.31× | 启动即装 5421 类，没有 CDS/惰性加载 |

### 一句话结论

**真赢的只有三样：启动快 5×、常驻内存省 8×、对象头小一半（空对象 8 B vs 16 B）；
并行扩展效率（8 线程 6.9× vs 3.9×）也更好，但那是效率不是绝对值。**

**输的是吞吐（解释 108×、JIT 5.6×）和 GC 停顿（最大 4×、总 4×）与分配峰值内存（2.6×）——
前者的原因是结构性的（逐条解释 / 静态整方法直译，没有 C2 那套内联与循环优化），
后者的原因是我们的堆是整块连续内存 + STW 回收，没有 G1 的分区并发。**
